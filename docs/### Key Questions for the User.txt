### Key Questions for the User:
1. **Unit System Strategy**: 단일 프로젝트 내에서 Inch와 Metric을 혼용해야 합니까, 아니면 프로젝트 설정(Layer 1)에서 하나만 선택하도록 강제합니까?
2. **Mandatory Atomic Attributes**: 모든 부품군(Pipe, Fitting, Valve 등)이 공통적으로 가져야 하는 "최소 원자 속성"은 무엇입니까? (예: Material, Grade, Manufacturing Method, Standard)
3. **Item Code Logic**: Item Code(Commodity Code) 생성 규칙은 고정입니까, 아니면 프로젝트별로 템플릿화하여 변경 가능해야 합니까?
4. **Data Normalization**: 최종 출력물에서 모든 데이터를 하나의 시트에 통합할까요, 아니면 현재처럼 부품군별로 시트를 분리하여 유지할까요?
5. **Vendor Data Handling**: 표준 규격품(Standard)과 벤더 특정 제품(Vendor-specific)을 스키마 레벨에서 어떻게 구분하여 관리하길 원하십니까?


### Answer of the User:
프로젝트 단위 체계는 하나(Inch 또는 Metric)로 강제합니다.
단, 물리적 규격 자체가 두 단위 체계의 조합으로 정의되는 아이템은 예외로 취급합니다. 예를 들어 Metric-to-Fraction Tubing Item의 8mm x 1/2"는 단위 변환의 문제가 아니라, 해당 아이템 고유의 속성 표기 규칙으로 분류합니다. 따라서 프로젝트 전역 단위 설정과 무관하게 원래 표기 방식을 유지해야 합니다.
이 예외를 수용하기 위한 구조적 방향을 아래 두 가지로 제시하니, _explode_size_range 함수 및 Phase 1~5 전체 아키텍처와의 일관성을 기준으로 검토 후 권고안을 제시해 주십시오.
방향 A — Item 레벨 단위 오버라이드
project_config.json에서 프로젝트 단위를 전역 선언하되, 특정 Item_Code 또는 Group에 한해 "unit_override": "mixed" 예외 플래그를 허용합니다. 해당 아이템의 Size 필드는 단일 값 대신 { "size1": "8mm", "size2": "1/2\"" } 형태의 구조체로 처리합니다.
방향 B — Size 필드의 타입 다형성(Polymorphism)
Size 필드 자체를 string | object로 다형적으로 설계합니다. 일반 NPS 값은 숫자로, 혼합 규격 아이템은 구조체로 저장하며, 출력 시 formatter.py(Phase 4)에서 타입에 따라 다르게 렌더링합니다.
두 방향 모두 Layer 4 Attribute Map 설계와 직접 연결되므로, Phase 1의 project_config.json 스키마 확정 전에 방향 결정이 필요합니다.
